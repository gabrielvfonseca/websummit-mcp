# PLAN.md: Web Summit MCP server on the attendee API You are building an MCP server that signs in to the **Web Summit attendee platform** with the user's own ticket and calls its API. It does **not** scrape websummit.com. Read this whole file before you write any code. Work phase by phase, and stop at each **GATE** to report to the user. ## 0. Context - **Event:** Web Summit Lisbon, 9â€“12 November 2026 (Lisbon time = UTC+0 in November). - **Attendee web app:** https://attend.websummit.com/lis26. Sign-in is by email: the user enters the address on their ticket, gets a one-time code by email, and enters it. The event slug is `lis26`. - **Mobile apps:** iOS `id6748312475`, Android `com.summitengine.attendee`. They probably share a backend with the web app. - **No public API docs exist.** The API is whatever the web app calls. You discover it by recording the web app's network traffic while the user is signed in. - **Existing scaffold** (from the scraping version) that you can reuse: - `src/agenda.ts`: clash detection, free slots, .ics export - `src/http.ts`: concurrency limiter and retry pattern - `src/index.ts`: tool registration style - Delete `src/parse.ts`, `src/discover.ts` and `src/urls.ts`. Nothing should fetch websummit.com HTML. - **Stack:** Node 20+, TypeScript (ESM, NodeNext), `@modelcontextprotocol/sdk` ^1.20, `zod` ^3.25, `playwright` (dev only, for discovery and the login fallback), `vitest`. ## 1. Guardrails (non-negotiable) 1. **Only the user's own account.** The user types their email and the code themselves. Don't read their inbox or automate the code step unless they explicitly ask you to. 2. **Never expose secrets.** Never print, log, commit or return tokens, cookies or codes in tool output. Redact them in HAR files, fixtures, docs and error messages: replace values with `REDACTED`, and keep only the header names. 3. **Don't defeat protections.** If sign-in or the API depends on a CAPTCHA, device attestation, certificate pinning, request signing you'd have to reverse-engineer, or anything that looks like bot protection, **stop and ask the user**. Don't decompile the mobile apps. 4. **Be polite with traffic.** At most 2 requests per second and 2 at a time. Back off on 429/5xx and respect `Retry-After`. Never bulk-export the attendee directory: people search is capped at 25 results per call and has no "get all" tool. 5. **Writes need consent.** Any action another person can see (connection requests, meeting requests, messages) must: - be behind the feature flag `WEBSUMMIT_ENABLE_SOCIAL=1` (off by default) - take a `confirm: boolean` argument - when `confirm` is false, return only a preview of exactly what would be sent 6. **Personal schedule writes** (bookmarking a session) are allowed without the flag. They're reversible and only the user sees them. 7. If the user's account doesn't allow a feature (for example, meetings for investors only), report it. Don't work around it. ## 2. Phase 1: Discover the API **Goal:** a written map of every endpoint the server needs, with redacted sample responses. 1. Write `scripts/record.ts`. It launches headed Chromium with Playwright, using `recordHar: { path: 'captures/session.har', content: 'embed' }`, and opens `https://attend.websummit.com/lis26`. Then it waits while the user signs in by hand. 2. Print this checklist and ask the user to do each step in the app, pressing Enter in the terminal after each one. Log a marker before each step so you can split the HAR file: 1. Finish signing in (email â†’ code) 2. Open the schedule; switch days; filter by a track; scroll until more sessions load 3. Search sessions for "AI" 4. Open one session 5. Bookmark that session, then remove the bookmark 6. Open "My schedule" 7. Open the speakers list and one speaker profile 8. Search attendees for a company name; open one profile 9. Open the companies or startups list; filter by industry; open one company 10. Open connections, meetings and recommendations, if present (read only; don't send anything) 11. Leave the tab idle for 15 minutes or more, then click something. This captures token refresh. 3. Write `scripts/analyze-har.ts`. For each request it outputs the host, method, path template (IDs replaced with `:id`) and status. It also records: - the auth mechanism: which header or cookie carries it, and its format - for GraphQL: `operationName`, whether it uses persisted queries (`extensions.persistedQuery.sha256Hash`), and the variables shape - pagination style (cursor, page/offset or limit) - any required custom headers (event id, app version, client id) - the sign-in calls (request code, verify code, refresh token) - token lifetime (if the token is a JWT, decode `exp` locally; don't send it anywhere) 4. Write the results: - `docs/api-map.md`: one table row per endpoint (purpose, method and path or GraphQL operation, auth, pagination, notes) - `fixtures/*.json`: one redacted sample response per endpoint - Add `captures/` to `.gitignore` and delete the raw HAR files once the fixtures exist. 5. Check auth replay: one minimal Node `fetch` call to the "my schedule" endpoint using the captured token, with only the headers you think are required. Record which headers turned out to be necessary. ### GATE 1: report to the user, then wait - Sign-in type, token lifetime, and whether refresh works. - Whether the sign-in steps can be called directly over HTTPS (no CAPTCHA or bot challenge). This decides between auth path A and path B below. - Which of these exist: sessions, my schedule (read and write), speakers, attendee search, companies, connections, meetings, recommendations. - Anything that triggered guardrail 3. - A proposed v1 tool list. The user confirms the scope before you continue. ## 3. Phase 2: Authentication (`src/auth/`) Build the first of these paths that works: **Path A: direct sign-in (preferred).** Use this if the sign-in calls are plain HTTPS. - `auth_start({ email })` calls the request-code endpoint and returns "Code sent to j***@domain". - `auth_verify({ code })` calls the verify endpoint and stores the tokens. **Path B: browser sign-in.** Use this if direct sign-in isn't viable. - `npm run login` opens headed Chromium at the app. The user signs in. - The script reads the token from the place found in Phase 1 (a response body, localStorage or a cookie) and saves it. - The `auth_start` tool returns instructions to run `npm run login`. **Common to both:** - **Override:** if `WEBSUMMIT_TOKEN` is set, it takes priority. This is for debugging only. - **Storage:** `~/.websummit-mcp/credentials.json` with file mode `0600`. It holds access token, refresh token, expiry, the masked email and the event slug. - **Refresh:** refresh before expiry. On any 401, refresh once and retry once. If that still fails, every tool returns a structured `auth_required` error that tells the user to run `auth_start`. - **Other tools:** - `auth_status` returns signed in yes/no, masked email, expiry and event. It never returns the token. - `auth_logout` deletes the stored credentials. - **Tests:** refresh on 401, expiry handling, and that no token ever appears in any tool result or log line (add a test helper that checks the output for token-shaped strings). ## 4. Phase 3: API client (`src/api/`) - **`client.ts`:** one `request()` function that handles: - the base URL from the API map - required headers, with a user agent of `websummit-mcp/` - auth injection - rate limiting (token bucket: 2 per second, at most 2 in flight) - retries (429/5xx, `Retry-After`, at most 3 attempts) - timeouts (20 s) - typed errors (`AuthRequired`, `NotFound`, `RateLimited`, `Upstream`) - **GraphQL:** if the API uses GraphQL, store each operation in `src/api/operations.ts`, copied exactly from Phase 1 (query text or persisted hash). Don't invent fields. - **`schemas.ts`:** a zod schema for every response used, written with `.passthrough()` and optional fields so new upstream fields don't break parsing. If parsing fails, log the path that failed and the field names (never the values), and return an `Upstream` error. - **`paginate.ts`:** an async iterator over whichever pagination style the API uses, with a hard `maxItems`. - **`src/domain.ts`:** stable internal types (`Session`, `Person`, `Company`, `Meeting`) and mappers from API shapes. Tools only ever work with domain types. Session times are ISO strings converted to Lisbon local `date`, `start` and `end`, so `agenda.ts` keeps working. - **Cache:** in-memory TTL. Schedule, speaker and company lists: 10 minutes. Details: 5 minutes. "My schedule": 30 seconds, and cleared after any write. ## 5.
